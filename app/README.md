# Maison de Gourmet — Christmas Tree Stamp Collection V1.3

Maison de Gourmet의 겨울·크리스마스 시즌 한정 컬렉션 화면입니다. 지정 민트 **#C8D7C3**와 레드 **#B61219**로 1·2·3·4개씩 총 10개 방울의 트리를 구성합니다. V1.3은 옅은 점선 윤곽의 미수집 상태와 붉은 채움·이중 링·체크의 수집 완료 상태를 명확히 구분합니다. V1.1의 Flask + Waitress + SQLite, 중앙 QR 판독, 조건부 재방문 자동 적립, 지급 버튼 한 번 누르기를 유지합니다. 실제 배포와 기존 DB 초기화는 하지 않았습니다.

| 먼저 볼 문서 | 내용 |
| --- | --- |
| `DESIGN_NOTES.md` | 지정 팔레트·도장 상태·모바일 렌더 설명. 실제 캡처로 표시하지 않음 |
| `STAMP_ART_GUIDE.md` | 이후 사진 기반 라인드로잉을 교체할 파일·상품 매핑·48×48 SVG 규격 |
| `MOBILE_TEST_GUIDE.md` | 운영과 분리한 휴대폰 HTTPS 연결 준비, iPhone Safari / Galaxy Chrome 각각의 체크리스트 |
| `CHANGELOG.md` | V1.2 → V1.3 변경 요약 |
| `TEST_REPORT.md` | 자동 검증 결과와 아직 사람이 직접 확인할 범위 |

**기존 event.json은 수정하지 않았습니다.** 카페명과 겨울 이벤트 문구는 표시 전용인 `static/app.js`의 `BRAND` 및 HTML에 반영합니다. 상품명·상품 ID·기간·보상은 계속 기존 event.json에서 읽습니다. 파일에 남아 있는 이전 임시 카페명/제목과 고객 화면의 새 브랜드 표시가 다른 것은 원본 설정 보존을 위한 분리입니다. 행사 날짜나 실제 보상을 새로 정한 것은 아닙니다.

## V1 / V1.1 / V1.2에서 바꿔 쓰기

앱을 중지하고 기존 DB를 제공된 백업 명령으로 백업한 뒤, **기존 프로젝트 폴더의 소스 파일만** 교체하세요. `data/`, 기존 `event.json`, 확정한 `Caddyfile`, 실제 실행 명령의 도메인·DB 경로를 보존해야 합니다. ZIP의 임시 `event.json`으로 운영 설정을 덮어쓰지 마세요. 새 폴더에서 기본 명령으로 시작하면 새 DB가 생기므로 기존 고객·QR을 이어 쓰려면 기존 DB 경로를 명시하세요. DB 초기화·마이그레이션·QR 재발급은 필요하지 않습니다.

```sh
.venv/bin/python manage.py --config /기존/폴더/event.json --database /기존/폴더/data/collection.sqlite serve --public-url https://실제도메인
```

위 경로와 도메인은 실제 값으로 바꿉니다. HTML·CSS·app.js·collection-core.js와 신규 stamp-art.js/stamp-art.svg를 함께 복사하세요. app.py, schema.sql, manage.py, event.json, 의존성 파일, 스캔 판단 로직 collection-core.js는 V1.2와 동일합니다. 아래 빠른 실행과 localhost QR 생성은 **새 데모**를 시작할 때의 안내입니다.

## 바로 실행하기

Python 3.9 이상이 필요합니다. 터미널에서 이 README가 있는 `cafe-collection` 폴더로 이동한 뒤 실행하세요.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-lock.txt
.venv/bin/python manage.py serve --dev
```

노트북 브라우저에서 **http://127.0.0.1:8765** 를 엽니다. 종료는 `Ctrl+C`입니다. 설치 후 사이트 이용에는 외부 CDN이나 인터넷 API가 필요하지 않습니다. Python이 실행되는 폴더 안의 `data/collection.sqlite`가 영구 저장소이며, 작업 폴더를 옮길 때 함께 보존하세요.

**이 개발 주소는 노트북에서만 접속됩니다. 휴대폰에서 localhost를 열면 휴대폰 자신에게 접속합니다.** 휴대폰 카메라 테스트는 아래 HTTPS 준비 후 진행하세요. IP 주소의 일반 HTTP로 휴대폰에 열면 연속 카메라 스캔과 Secure 쿠키를 정상 검증할 수 없습니다.

## 실기기 테스트용 HTTPS 준비

카메라 권한과 Secure 쿠키를 실제로 점검하려면 인증서 경고 없는 HTTPS가 필요합니다. localhost의 보안 예외는 휴대폰에서 노트북 LAN IP를 여는 상황에 적용되지 않습니다. [MDN getUserMedia 설명](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

원본 설정을 건드리지 않는 V1.2의 테스트 준비 도구를 그대로 유지합니다. 아래 주소는 예시이며, **본인 노트북의 실제 LAN IP**로 바꾸세요.

```sh
.venv/bin/python tools/prepare_mobile_test.py --origin https://192.168.0.20:8443 --out work/mobile-test
```

새 폴더의 `RUN.md`에 테스트 서버·기존 HTTPS 프록시(Caddy)·QR 생성 명령이 준비됩니다. 테스트 설정 사본에만 임시 기간과 draft=false를 넣고, 별도 DB 경로를 지정합니다. 서버 실행·인증서 설치·시스템 신뢰 변경은 자동 수행하지 않습니다. Caddy 실행과 휴대폰 인증서 신뢰를 사람이 확인한 뒤 테스트하세요. **포트만 달라도 쿠키는 같은 호스트에서 공유될 수 있으므로 운영과 다른 호스트나 분리한 테스트 브라우저 저장소를 사용합니다.**

단계별 준비와 기기별 체크리스트는 `MOBILE_TEST_GUIDE.md`에 있습니다. 기존 개발 모드의 LAN HTTP 제한이나 운영 HTTPS 시작 조건을 완화하지 않았습니다.

## 상품 QR을 만들어 시험하기

별도 터미널에서 실행합니다.

```sh
.venv/bin/python manage.py qr-export --public-url http://127.0.0.1:8765
```

생성된 `qr-export/index.html`을 파일로 엽니다. 상품별 링크를 열고 첫 방문에는 **새 스탬프판 만들고 적립하기**를 누릅니다. 재방문은 조건을 확인하면 자동 적립하고, 확인할 수 없으면 수동 버튼을 표시합니다. 다른 상품 링크를 자유로운 순서로 열고, 같은 상품을 다시 열어 중복되지 않는지 확인하세요. 이 페이지는 운영자의 QR 확인용이며, 물리적 보드의 크기·덮개·배치 시안은 포함하지 않습니다.

QR 10개는 `/q/<추측하기 어려운 고정값>` 형식입니다. 같은 DB에서 다시 내보내도 고정값이 유지됩니다. 고객 스탬프판에는 QR 원문이나 전체 QR 목록을 내려보내지 않습니다. QR 파일과 `manifest.json`은 운영자만 보관하고, 고객용 서버 경로에 올리지 마세요.

## 고객 동선과 구현 범위

1. **첫 구매:** 기본 카메라로 상품 QR → 상품 확인 화면과 모바일 스탬프판 → `새 스탬프판 만들고 적립하기` → 쿠키 저장 확인 후 적립. 새 고객을 자동 생성하지 않습니다.
2. **다음 구매:** 같은 브라우저의 유효한 세션이 확인되고 아래 자동 적립 조건을 만족하면 추가 버튼 없이 POST로 적립합니다. 이미 모은 상품은 POST 없이 안내합니다. 조건을 확인할 수 없으면 `이 상품 스탬프 받기` 버튼을 남깁니다. 순서는 자유입니다.
3. **2~3종 동시 구매:** `QR 연속 스캔하기` → **QR 전체를 중앙 네모 안에 넣고 중심을 십자에 맞춘 뒤 잠시 정지** → 3회 연속 같은 QR이 판독되면 적립. 네모 밖은 판독 영상에서 제외합니다. 여러 QR이 판독되거나 QR이 테두리에 걸리거나 중심이 십자를 벗어나면 적립하지 않습니다. 이미 처리한 QR은 스캐너를 닫을 때까지 다시 POST하지 않습니다. 영상은 기기 안에서만 처리합니다.
4. **권한 거부·미지원:** 기본 카메라로 하나씩 열고, 최초 방문 또는 자동 적립 조건을 확인하지 못한 경우 버튼으로 적립합니다. 상품명을 선택해 적립하는 우회 기능은 없습니다.
5. **기록 보관:** 개인 복구 링크는 선택 사항입니다. 발급 후 개인 메모에 저장하세요. 새로 발급하면 이전 링크는 즉시 무효가 됩니다.
6. **10종 완성:** 보상 지급 대기 화면의 위험 안내를 읽고, 직원이 실물을 지급한 뒤 **`직원용 · 실물 지급 완료 (1회 처리)` 한 번만** 누릅니다. PIN·로그인·체크박스·추가 확인창은 없습니다. 요청 중에는 버튼을 비활성화하고, 완료 후에는 숨기고 비활성화합니다. 서버 기록과 10개 스탬프는 계속 남습니다.

트리 방울은 상품 순서대로 1·2·3·4개씩 배치되며 각 상품에 1:1 대응합니다. 미수집은 민트 점선/옅은 바탕/약한 아이콘, 완료는 레드 채움/밝은 그림/이중 링/체크로 구분합니다. 색상 외에 채움·대비·형태 차이도 적용합니다. 방울을 누르는 것으로 적립되지 않습니다. 긴 상품명은 한 줄로 줄여 표시하고 전체 이름은 접근성 레이블과 툴팁에 남깁니다. `n / 10 collected`와 완료 후 기록 유지 규칙은 그대로입니다.

### 재방문 자동 적립 조건과 한계

자동 적립은 QR 페이지의 **최초 로딩 1회**에만 검토하며 다음 조건이 모두 필요합니다.

- GET 요청에 `Sec-Fetch-User: ?1`, `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`가 있고 Purpose/Sec-Purpose/X-Purpose 값이 없어야 합니다. 지원하지 않거나 신호가 빠진 브라우저는 수동 버튼으로 진행합니다.
- 브라우저의 Navigation Timing 유형이 `navigate`여야 합니다. `reload`, `back_forward`, 판별 불가는 자동 적립하지 않습니다.
- 최초부터 화면이 표시되고 현재도 표시·포커스 상태여야 합니다. prerender 상태와 이미 활성화된 prerender, 로딩 중 앱 전환·페이지 이탈 이력이 있으면 수동 처리합니다.
- 서버가 유효한 기존 고객 세션과 CSRF 토큰을 반환해야 하며, 적립 기간이고 미수집·미지급 상태여야 합니다.

POST 전에 해당 방문 기록에 시도 표시를 남깁니다. 응답 유실 시 상태 조회로 기록을 확인하며 자동으로 POST를 재시도하거나 새 고객을 만들지 않습니다. 화면 재표시·뒤로 가기·다시 불러오기 버튼도 자동 적립을 재실행하지 않습니다. 서버의 상품별 유일키는 동시 수동/자동 요청에도 중복 적립을 막습니다.

**브라우저 신호만으로 실제 QR 스캔과 일반 링크 클릭·주소 입력을 완벽하게 구분할 수 없습니다.** 유효한 기존 세션으로 정상 화면에서 QR URL을 직접 열면 자동 적립될 수 있습니다. 로그인 없이 구매를 검증하지 않는 고정 QR 정책의 한계이며, 모든 종류의 미리보기를 완벽하게 차단한다고 보장하지 않습니다. 이 위험을 수용할 수 없다면 직원 운영에서는 웹 내 중앙 스캐너를 사용하거나 자동 적립 대신 수동 확인 정책으로 돌아가야 합니다. 이번 버전은 판별이 불확실한 경우에 수동 확인을 유지합니다.

### 중앙 판독 영역의 구현과 제한

실제 video 요소와 중앙 테두리의 안쪽 좌표를 매 프레임 측정합니다. 영상 크기, `object-fit: cover/contain`, 중앙 `object-position`을 반영해 원본 프레임 좌표로 역변환하고 **동일한 crop canvas**를 BarcodeDetector와 jsQR에 전달합니다. 화면 회전 시 메타데이터와 레이아웃을 다시 측정하며, 판독 중 크기가 바뀐 프레임은 버립니다. 브라우저가 제공하는 `videoWidth/videoHeight`는 drawImage 프레임의 방향이므로 화면 방향을 다시 회전시키지 않습니다. 비정상 좌표나 지원하지 않는 CSS 변환에서는 전체 영상으로 우회하지 않습니다.

BarcodeDetector의 복수 결과는 모두 거부합니다. jsQR은 한 번에 한 코드만 반환하므로 첫 코드의 사각형을 가린 뒤 다시 판독하여 다른 코드가 있으면 거부합니다. 단일 후보도 전체 모서리가 영역 안에 있고 중앙 십자를 덮어야 하며, 같은 위치 조건에서 3개 연속 프레임이 필요합니다. **흐리거나 가려져 판독되지 않는 QR의 존재까지 검출하는 기능은 아닙니다.** 반사·초점·기종별 방향 처리와 성능은 실제 휴대폰에서 추가 검증해야 합니다.

쿠키는 사람이나 휴대폰 자체를 식별하지 않습니다. Safari·Chrome·카카오톡·네이버 등의 앱 내부 브라우저는 저장소가 다를 수 있고, 브라우저/OS의 정책에 따라 쿠키가 삭제될 수도 있습니다. 인앱브라우저 경고는 알려진 사용자 에이전트에 대한 보조 안내이며 모든 앱을 완벽히 감지하지는 않습니다. **처음부터 같은 기본 브라우저를 사용**하고, 브라우저를 바꿔야 하면 개인 복구 링크를 사용하세요. 기록을 자동 병합하지 않습니다.

## 운영 전에 확정할 설정

향후 운영 정보를 확정할 때 `event.json`을 수정하고 서버를 다시 시작하면 적용됩니다. **이번 V1.3 작업에서도 파일을 보존했습니다.** 현재는 `draft: true`이고 날짜는 비워 둔 데모입니다. 실제 운영 모드에서는 데모 상태로 시작할 수 없습니다. 표시 전용 브랜드명/메인 문구는 event.json과 분리되어 있습니다.

| 설정 | 확정할 내용 |
| --- | --- |
| `cafe_name`, `title`, `description` | 보존된 행사 메타데이터. 고객 화면 브랜드는 BRAND/HTML에서 별도 표시 |
| `products[].name` | 시즌 음료 4종, 지정 상품 6종의 실제 이름 |
| `reward` | 실제 선물 및 수령 안내 |
| `starts_at` | 적립 시작 시각, 포함 |
| `ends_at` | 적립 종료 시각, 미포함 |
| `reward_until` | 선물 지급 마감 시각, 미포함 |
| `draft` | 운영 정보가 확정되면 `false` |
| 실행 인자의 `--public-url` | 고객이 계속 사용할 고정 HTTPS 주소 |

날짜는 `2026-11-01T00:00:00+09:00` 같은 시간대 포함 ISO 8601 형식입니다. 이 값은 형식 예시이며 실제 일정이 아닙니다. 적립 기간은 최대 32일로 제한하며, 시작 < 종료 ≤ 지급 마감이어야 합니다. 표시 날짜는 한국 시간 기준입니다. 적립은 서버 시간을 기준으로 판단하므로 노트북의 자동 날짜/시간을 켜 두세요.

`event.id`와 `products[].id`는 운영 시작 후 바꾸지 마세요. 기존 DB와 다른 이벤트/상품 ID로 서버를 시작하면 오류를 내어 잘못된 재사용을 막습니다. 이름은 바꿀 수 있지만, 진행 중 상품 자체를 교체하면 기존 수집 기록과 의미가 달라집니다. 이 앱은 한 행사 전용이며, 행사 변경을 위한 고객 초기화 기능은 제공하지 않습니다.

## 노트북에서 HTTPS로 운영하기

HTTPS 종단도 같은 노트북에서 실행합니다. Caddy가 HTTPS를 처리하고 앱은 `127.0.0.1:8765`에서만 받습니다. 운영 도메인이 정해지지 않아 DNS·인증서·방화벽·공유기 설정을 실제로 변경하지 않았습니다.

1. 노트북으로 도달하는 고정 도메인/DNS를 준비합니다. 외부 고객에게 공개하려면 외부 80/443 → 노트북 연결이 필요합니다. 공유기 포트 전달이나 방화벽 설정이 필요할 수 있고, 통신사 CGNAT 환경에서는 직접 공개가 불가능할 수 있습니다. 매장 Wi-Fi 전용 운영도 선택할 수 있지만 고객이 해당 Wi-Fi에 연결해야 합니다. 도메인과 접속 범위는 실제 환경 확인 후 정하세요.
2. `event.json`의 정보와 날짜를 확정하고 `draft`를 `false`로 설정합니다.
3. Caddy 공식 배포본을 설치한 뒤 `Caddyfile.example`을 `Caddyfile`로 복사하고 실제 도메인으로 바꿉니다. 인증서 발급 조건과 외부 연결을 확인합니다.
4. 다음 두 명령을 각각 터미널에서 실행합니다. `stamp.example.com`은 예시이며 실제 도메인으로 바꾸세요.

```sh
.venv/bin/python manage.py serve --public-url https://stamp.example.com
caddy run --config Caddyfile
```

5. **실제 HTTPS 주소로 QR을 다시 내보냅니다.** 개발용 localhost QR을 매장에서 사용하지 마세요.

```sh
.venv/bin/python manage.py qr-export --public-url https://stamp.example.com
```

6. 아이폰 Safari와 안드로이드 Chrome에서 아래 점검을 끝낸 후 고객에게 안내합니다.

기본 앱은 수면 모드나 전원 차단 중에는 작동하지 않습니다. 행사 중 노트북의 전원·네트워크 연결을 유지하고 잠자기를 해제하세요. 서버·Caddy의 자동 시작은 OS에 맞춰 별도로 설정해야 합니다. 외부 호스팅이나 터널 서비스는 이 MVP에 추가하지 않았습니다.

## 보안 및 의도적으로 남은 한계

- **구매 검증 없음:** 고정 QR을 아는 사람은 구매 없이도 적립할 수 있습니다. QR을 공유하면 원격 적립이 가능하고, 쿠키를 지우거나 다른 브라우저를 쓰면 별도 고객이 될 수 있습니다. 긴 QR 값과 요청 제한은 추측/반복을 줄일 뿐 구매 증명이나 1인 1회 보장이 아닙니다. 노출을 통제하는 매장 운영이 필요합니다. QR 보드의 물리적 대책은 협의 보류 상태입니다.
- **직원 인증 없음:** 지급 버튼은 해당 고객 쿠키 또는 복구 링크를 가진 누구나 누를 수 있습니다. V1.1에서는 운영 정책에 따라 체크박스와 확인창을 없앴으므로 한 번의 오조작도 지급 완료로 기록됩니다. 화면의 경고는 인증이나 취소 기능이 아닙니다. 서버는 10종 완성과 미지급 상태를 확인하고, 트랜잭션 안에서 고객당 지급 기록을 1개만 남깁니다. 실제 물품 전달 여부와 직원 신원은 검증하지 못합니다.
- **GET은 읽기 전용:** QR·복구 링크·미리보기·HEAD 요청은 서버 레코드를 변경하지 않습니다. 기존 세션의 QR 페이지에서는 위 조건에 따라 JavaScript가 별도의 적립 POST를 보낼 수 있습니다. 신규 생성·복구·지급은 사용자 버튼, 웹 내 연속 적립은 중앙 스캐너의 판독이 POST의 계기입니다. Origin·JSON·CSRF 검증은 유지했습니다.
- **쿠키:** 운영 시 `__Host-collection`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, Domain 미지정. 256비트 무작위 세션 토큰의 SHA-256 해시만 DB에 저장합니다. 개발 모드만 localhost용 비보안 쿠키를 사용하며 LAN HTTP 주소는 거부합니다.
- **CSRF/요청:** 변경 요청은 설정된 Origin, JSON, 전용 헤더를 요구하고 기존 세션에는 별도 CSRF 토큰을 검증합니다. Host 검증, 본문 크기 제한, 제한된 요청 횟수, 프레임 차단, CSP, `no-store`, `no-referrer`를 적용합니다. 운영 HTTPS에는 HSTS를 추가합니다.
- **복구 링크:** 256비트 난수, DB에는 SHA-256 해시만 저장, 90일 유효. URL의 `#fragment`에 실어 일반 HTTP 요청·서버 접근 로그·리퍼러에 토큰이 들어가지 않게 했습니다. 화면 로딩 즉시 주소창의 fragment를 지우고 명시적 복구 버튼을 눌렀을 때만 POST 본문으로 전송합니다. 복구 링크를 가진 사람은 기록에 접근하고 지급 처리를 할 수 있으므로 비밀번호처럼 보관하세요. 다른 기록이 있는 브라우저에 복구할 때는 교체 확인이 필요하며 병합하지 않습니다.
- **보관 기간:** 세션과 복구 링크는 발급 후 90일, 고객/스탬프/지급 데이터는 운영자가 별도로 보관·삭제할 때까지 DB에 남습니다. 90일은 접근 유효 기간이며 DB 자동 삭제 기간이 아닙니다. 복구 링크와 쿠키를 모두 잃으면 식별 정보가 없어 고객의 기록을 찾을 수 없습니다.
- **저장 및 용량:** SQLite WAL, 외래키, `(customer_id, product_id)` 기본키, 단일 트랜잭션의 지급 갱신/감사 기록을 사용합니다. Waitress 1개 프로세스/32개 작업 스레드 기준입니다. 400명/동시 30명은 검증 목표이며 가입자 수를 400명으로 막지는 않습니다. 다중 서버나 공유 네트워크 드라이브는 지원 범위가 아닙니다.
- **개인정보 최소화:** 이름·연락처·이메일·카메라 영상을 저장하지 않습니다. 요청 제한용 IP 키는 프로세스 메모리에만 일시 보관합니다. 별도 분석기나 CDN을 넣지 않았습니다. DB에는 세션 관련 정보와 발급된 링크 해시가 있으므로 백업도 비공개로 보관하세요.

관련 구현 근거: [Flask 보안 지침](https://flask.palletsprojects.com/en/stable/web-security/), [SQLite WAL](https://www.sqlite.org/wal.html), [MDN 카메라 보안 컨텍스트](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [BarcodeDetector 지원 제한](https://developer.mozilla.org/en-US/docs/Web/API/Barcode_Detection_API), [jsQR 공식 저장소](https://github.com/cozmo/jsQR). BarcodeDetector가 없으면 사이트에 포함한 jsQR로 QR을 읽습니다.

## 백업과 복원

실행 중인 WAL 모드 DB 파일만 복사하지 말고 제공 명령을 사용하세요.

```sh
.venv/bin/python manage.py backup data/collection-2026-10-29.backup
```

새 파일로만 백업되며 기존 백업을 덮어쓰지 않습니다. 하루 종료 시 등 정해진 주기로 비공개 위치에 보관하세요. 백업 날짜는 예시입니다.

복원은 먼저 앱을 중지한 후 기존 `data` 폴더 전체를 별도 위치에 보존하고, **새 빈 폴더**에 백업 파일을 `collection.sqlite`로 복사합니다. `--database /새/폴더/collection.sqlite`를 지정해 서버를 시작합니다. 오래된 WAL/SHM 파일과 백업 DB를 섞지 마세요. 복원 후 최근 적립·지급 내역이 백업 시점으로 돌아가므로 지급 누락/중복 위험을 직원 기록과 대조해야 합니다.

```sh
.venv/bin/python manage.py --database /새/폴더/collection.sqlite serve --public-url https://stamp.example.com
```

## 자동 테스트

Python 테스트와 함께 프런트엔드 회귀 검사를 실행하려면 **Node.js 18 이상**이 필요합니다. 브라우저 시뮬레이션·QR 픽셀 검사를 위한 개발 도구이며 운영 서버에 Node.js는 필요하지 않습니다. npm 패키지 추가는 없습니다. Node가 없으면 검사를 건너뛰지 않고 명확히 실패합니다.

```sh
.venv/bin/python -m pytest -q
```

기존 V1.2의 pytest 40개와 프런트엔드 38개 시나리오를 유지하고, 지정 색상/밝은 잉크 대비, 고정 그림 영역, 상품별 SVG 매핑, 도장 링·체크 상태와 아이콘 대안을 검사합니다. 프런트엔드 검사는 실제 app.js와 작은 DOM/HTTP 모형을 사용하며 실제 브라우저·실물 카메라 테스트는 아닙니다. 400명 컬렉션·4,000개 스탬프·400개 지급 기록 및 DB 무결성 검사도 유지합니다. 테스트 DB는 임시 폴더를 사용합니다. 정적 좌표 계산 통과는 실제 화면 겹침이 없다는 실기기 검증을 뜻하지 않습니다.

프런트엔드 검사만 따로 실행할 수 있습니다.

```sh
node --test tests/scanner.test.cjs tests/app-flow.test.cjs
```

실제 HTTP 테스트는 **별도 데모 DB와 서버**를 사용합니다.

```sh
.venv/bin/python manage.py --database data/http-test.sqlite qr-export --public-url http://127.0.0.1:8766 --out data/http-qr
.venv/bin/python manage.py --database data/http-test.sqlite serve --dev --port 8766
```

다른 터미널에서 실행합니다.

```sh
.venv/bin/python tests/http_smoke.py data/http-qr/manifest.json
```

30명의 가상 고객을 만들고, 480개 HTTP 요청의 오류·지연 시간을 확인합니다. localhost 데모에만 실행되며 실제 행사에는 사용할 수 없습니다. 같은 서버에서 반복하면 요청 제한에 도달할 수 있으므로 1분 이상 간격을 두세요.

## 휴대폰 실물 점검 — 운영 전 필요

- [ ] 실제 HTTPS 도메인이 매장 Wi-Fi와 고객 모바일 데이터에서 의도한 범위로 접속된다.
- [ ] 아이폰 Safari / 안드로이드 Chrome에서 첫 QR → 확인 → 적립 → 새로 열기 시 기록이 유지된다.
- [ ] 두세 상품을 연속 스캔하고 같은 QR을 계속 비춰도 각 1개만 적립된다.
- [ ] 네모 밖/테두리/십자 밖의 QR은 적립되지 않고, 네모 안에 여러 개가 있을 때 임의 상품이 적립되지 않는다. BarcodeDetector와 jsQR 경로를 각각 확인한다.
- [ ] 세로·가로 회전, 화면 확대, 초점·반사·조명 변화에서 화면 영역과 판독 영역이 일치한다.
- [ ] 첫 방문에는 시작 버튼이 필요하고, 재방문은 브라우저 신호가 있는 경우에만 자동 적립된다. 신호가 없으면 수동 버튼으로 적립된다.
- [ ] 링크 미리보기·사전 로딩·새로고침·뒤로 가기·앱 전환 복귀에서 자동 적립이 발생하지 않는다.
- [ ] 카메라 권한 거부 시 대안이 보이고 기본 카메라로 상품별 적립이 가능하다.
- [ ] 스캐너 닫기·앱 전환 후 카메라 사용 표시가 꺼진다.
- [ ] 인앱브라우저와 기본 브라우저 간 기록 분리를 확인하고 복구 링크로 옮긴다.
- [ ] 쿠키 차단·시크릿 모드·링크 복사 실패 안내를 확인한다.
- [ ] 10종 완성 → 지급 대기 → 실물 지급 후 버튼 한 번 → 완료, 연타·네트워크 오류·다시 열기에도 지급 기록 1개와 스탬프 10개가 유지된다.
- [ ] 새 복구 링크 발급 후 이전 링크가 무효가 되고, 별도 브라우저에서 복구된다.
- [ ] 운영 시작/마감, 보상 지급 마감, 노트북 재시작, 백업/복원을 실제 운영 방식으로 확인한다.

검증 결과와 미검증 항목은 `TEST_REPORT.md`, 배포 전 필수 확인 사항은 `PRE_DEPLOY_CHECKLIST.md`에 기록했습니다. QR 보드의 물리적 크기·덮개·배치는 이번 변경에서 제외했습니다.

실기기 준비 및 **기기별 결과를 기록할 체크리스트**는 `MOBILE_TEST_GUIDE.md`를 사용하세요. iPhone Safari와 Galaxy Chrome의 카메라·인앱브라우저·실제 표시 검증은 아직 완료하지 않았습니다.
