## 고객 화면과 데이터

| 동작 | 서버와 브라우저의 처리 |
|---|---|
| 처음 접속하거나 QR을 엶 | GET·HEAD는 카드·세션·적립을 만들지 않는다. 이름, 휴대전화번호, 기본 미선택 개인정보 안내 확인란을 표시한다. |
| 등록 제출 | `POST /api/register`가 안내 확인을 검사한다. `BEGIN IMMEDIATE` 안에서 번호의 검색값을 조회하고 고객·프로필·세션을 함께 저장한다. `UNIQUE(phone_lookup_hmac)`가 DB에서도 한 번호에 한 카드를 보장한다. |
| 중복 번호 | 이름 일치 여부와 무관하게 409와 찾기 안내를 반환한다. 브라우저는 ‘기존 스탬프 찾기’를 주 버튼으로 표시하고 사용자가 누르면 같은 폼의 입력값을 이어 쓴다. 서버 응답은 기존 고객의 이름이나 적립 상태를 포함하지 않는다. |
| 쿠키 삭제·다른 브라우저 | `POST /api/find`에서 이름과 번호 검색값이 모두 일치하면 기존 고객 ID에 새 세션을 발급한다. 다른 브라우저의 세션도 계속 쓸 수 있다. 일치하지 않으면 재입력·정정 안내를 표시한다. |
| 재방문·구버전 카드 | 유효한 기존 쿠키로 카드를 바로 연다. 프로필이 없는 기존 고객은 원래 세션·개인 복구 링크를 사용한다. 새 프로필을 임의 연결하지 않는다. |
| 상품 QR과 보상 | 첫 등록·찾기 후에는 대기 중인 상품을 확인하고 적립 버튼을 누른다. 재방문에서는 기존 자동 적립 조건을 적용한다. 실제 적립은 POST, 상품당 1회이며 지급 기록도 고객당 1개다. |

전화번호는 국내 휴대전화 형식으로 해석한다. 010은 11자리, 기존 011·016·017·018·019는 10~11자리이며 공백·괄호·하이픈을 제거하고 `+82` 형식도 같은 국내 번호로 바꾼다. 이름은 앞뒤 공백만 제거한 1~80자로 비교한다. 가입·찾기 요청 한도는 1분간 IP당 120회, 정규화 번호당 합산 10회다. 기존 매장 공유 네트워크의 방문자를 고려해 두 기준을 함께 쓴다.

DB에는 이름, HMAC-SHA256 검색값, 안내 버전 `demo-v1`과 확인 시각을 저장한다. 프로필 입력은 같은 출처의 JSON POST 본문에만 전송하고 성공 또는 페이지 이탈 때 폼에서 지운다. 운영 설정의 브라우저 쿠키에는 90일짜리 무작위 세션 토큰이 들어간다. [실제 8개 테이블 ERD와 고객 데이터 흐름](../README.md#고객-등록과-기존-스탬프-찾기) · [스키마](../app/schema.sql)

## 마이그레이션과 운영 변경

기존 테이블을 교체하지 않고 `customer_profiles`를 추가한다. `metadata`에는 `profile_key_check_v1`이라는 키로 비밀 키 확인값을 저장한다. 스키마 생성과 확인값 저장은 같은 DB 트랜잭션에서 끝낸다. 이관을 반복해도 기존 행과 QR 값이 유지된다. 행사 서명 불일치, 기존 행사에서 상품 행 누락, 키 불일치, 프로필 테이블과 키 확인값 간 모순이 발견되면 이관을 중단한다.

키 파일은 DB별로 한 번 생성한다. DB 백업과 짝이 맞는 원래 키를 별도의 암호화 보관소에 보관해야 한다. 복원 후보와 현재 원본을 모두 검사한 뒤에만 Windows 운영 도구가 파일 교체를 진행한다. 이번 검증에는 새로 생성한 합성 DB만 사용했다. [백업·격리 복원 순서](BACKUP_RECOVERY.md#등록한-카드를-복원할-때-필요한-두-파일)

행사 상한은 연속한 긴 달 두 개를 수용하는 **62일**로 정했다. 시작 < 종료 ≤ 보상 마감 조건을 유지하며 행사 설정 예제의 실제 날짜 세 칸은 비어 있다.
