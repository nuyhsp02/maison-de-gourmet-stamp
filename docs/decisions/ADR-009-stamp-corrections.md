# ADR-009 · 적립 마감 후 관리자 예외 정정과 보상 자격 보호

- 결정일 — 2026-11-25. [행사 생명주기 결정](ADR-008-event-lifecycle.md)을 구체화한 사용자 정책이다.
- 상태 — 로컬 구현 및 합성 검증. 운영 계정 발급과 실제 DB 이관은 별도 승인 사항이다.

## 왜 일반 취소와 정정을 나누는가

적립이 끝난 뒤 완성 카드에서 한 개를 취소하면 고객은 그 스탬프를 다시 모을 수 없다. 한편 두 개를 모은 카드의 상품 기록이 실제 구매와 다를 때에는 2월에도 원래 적립 시각을 보존하며 고칠 수 있어야 한다. 기존 시스템에는 직원 자격 하나와 취소 감사 기록이 있었다. 기존 운영자 표기인 `admin_actor`는 해당 계정에 상위 권한을 부여하는 근거가 될 수 없다. [기존 직원 관리 설계](../PR2_STAFF_ADMIN.md)

| 행사 설정에서 읽은 KST 경계 | 일반 직원 | 별도 자격으로 인증한 관리자 |
|---|---|---|
| 적립 마감 전 | 기존 수령 전 취소 | 기존 수령 전 취소 |
| `ends_at <= now < reward_until` | 조회, 일반 취소는 409 | 불완전·미수령 카드의 기존 스탬프 교체 또는 제거 |
| 보상 마감 정각부터 | 조회 | 조회, 정정은 409 |

확정 일정에서 두 경계는 각각 2월 1일과 3월 1일 00:00 KST다. 3월 31일 고객 접근 종료와 개인정보 파기는 별도 작업이다.

## 권한과 카드 상태

기존 직원 비밀번호는 그대로 직원 로그인에 사용한다. 관리자는 운영자가 로컬 대화형 명령으로 별도 계정 ID와 비밀번호를 설정해야 한다. 비밀번호는 숨김 입력하며 역할별 파일에는 검증용 해시를 저장한다. 서버가 접속 경로에 맞는 자격을 검증하고 세션을 역할·계정·검증값에 묶는다. 요청 본문으로 역할을 지정할 수 없다. [설정 명령](../../app/manage.py) · [인증과 인가](../../app/staff_admin.py)

교체는 같은 카드에 없는 행사 상품으로만 가능하며 기존 적립 시각을 유지한다. 제거는 이미 보유한 한 개만 대상으로 한다. 두 동작 모두 총개수를 늘릴 수 없다. 모든 상품을 모은 카드는 검토 대상으로 남기고, 지급 완료 카드는 지급 이력과 함께 보존한다. 사용자가 요청한 권한 분리·사유 기록에 비추어, 기존 일반 취소 API에 관리자 우회 옵션을 붙이거나 보상 자격을 나중에 수동 복구하는 방안은 채택하지 않았다. UI 버튼만 숨기면 직접 요청에 같은 규칙을 적용할 수 없다.

## 잠금, 사유와 감사 기록

서버는 요청을 인증한 뒤 SQLite의 `BEGIN IMMEDIATE`로 쓰기 잠금을 얻는다. 그 안에서 세션·역할·CSRF, 서버 시각, 수령 여부, 정정 사유, 조회한 카드 버전, 적립 행을 다시 확인한다. 동시에 다른 직원이 카드를 바꾸거나 요청이 쓰기를 기다리는 동안 기간이 끝나면 예전 조회 결과로 변경할 수 없다. 요청 ID의 고유 제약은 같은 작업의 중복 처리를 막는다. [쓰기 트랜잭션](../../app/app.py) · [정정 API](../../app/staff_admin.py)

기존 일반 취소 이력은 그대로 보존한다. 관리자 정정에는 요청 ID, 카드 ID, 관리자 계정, 정정 시각, 유형과 사유 코드·상세, 전후 상품, 원래 적립 시각, 최종 스탬프 수, 전후 보상 자격을 별도 행에 기록한다. 사유에는 업무 사실만 10~300자로 적도록 안내하고 해당 카드의 이름과 일반적인 연락처 형태를 거른다. 자유 서술에서 타인의 이름까지 완전히 식별할 수는 없다. 감사 행 삽입이 실패하면 적립 행 변경도 롤백한다. 트리거는 기존 감사 행의 수정·삭제·충돌 덮어쓰기를 거부한다. DB 파일과 스키마를 직접 통제하는 운영자까지 제약하는 외부 변조 방지 저장소는 아니다. [정정 스키마](../../app/correction_schema.sql) · [검증 기록](../devlog/DEV-017-stamp-corrections.md)

## 이관과 복구

정정 이력은 명시적으로 이관한 DB에서만 사용한다. 이관 전에는 기존 조회·일반 취소가 가능하고 관리자 정정은 닫혀 있다. Linux 이관은 기존 서명과 QR·프로필 키의 짝을 먼저 검증하고, 감사 테이블·인덱스·트리거 및 새 서명을 한 트랜잭션으로 추가한다. 기존 DB 백업에 새 감사 행도 포함된다. 직원과 관리자 자격은 DB·프로필 키 백업과 별도로 보호·재설정해야 한다. [이관](../../deploy/linux/demo.py) · [백업과 격리 복원](../../deploy/linux/backup.py)

이관 뒤 신규 적립·정정이 발생하면 과거 백업으로 운영 원본을 덮어쓸 경우 그 이력을 잃는다. 문제가 생기면 정정 쓰기를 중지하고 최신 원본을 보존한 후, 격리 복사본에서 해당 스키마를 읽을 수 있는 버전으로 복구를 검증한다. 이전 스키마만 아는 Linux 버전으로의 단순 교체는 신규 서명 검증을 통과하지 못한다.
