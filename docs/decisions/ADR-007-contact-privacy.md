# ADR-007 · 카드 식별과 미수령 상품 연락을 위한 전화번호 보호

- 상태 — `aaccb50`에서 합성 구현 확인. 2026-11-25 사용자가 정식 운영의 연락 목적과 안내 UI를 결정했습니다. 실제 고객 가입은 차단 상태입니다.
- 이력 — [ADR-002](ADR-002-anonymous-identity.md)의 익명 카드·쿠키 이력에서 고객 프로필 방식으로 확장했습니다. 기존 HMAC 전용 카드는 그대로 찾을 수 있습니다. [당시 결정과 후속 지시](../evidence/portfolio-milestones-20261125.md#사용자-결정)

## 1. 해결하려던 문제

번호 한 개당 카드 한 장을 유지하려면 입력한 번호가 이전 번호와 같은지 판별해야 합니다. 매장에는 미수령 상품에 대해 고객에게 연락할 필요도 있습니다. 직원이 카드를 찾거나 적립을 취소할 때는 전체 번호를 다시 보여줄 필요가 없습니다.

## 2. 고려한 대안과 기록의 한계

D80의 접두·끝자리만 남기는 검토안은 직원 표시에는 충분하지만 전화를 걸 수 없습니다. D81에서 전체 연락처 보관 요구가 추가됐고 D84에서 기존 HMAC에 별도 암호문을 결합하는 설계를 검토했습니다. 선택 동의와 거부 시 카드 유지도 당시의 제안이었습니다. 사용자가 최종 선택한 **화면**은 안내 확인 한 칸입니다. 이 선택만으로 처리의 법적 근거가 정해지지 않습니다. 암호 방식 간 성능 비교 수치는 없습니다.

## 3. 최종 선택

- 카드 검색은 정규화한 번호의 키 있는 해시(HMAC-SHA256)와 SQLite UNIQUE 제약을 유지합니다. 신규 연락처는 별도로 공개키 sealed box로 암호화합니다. 기존 HMAC을 역산하거나 카드 찾기·직원 검색 입력으로 연락처를 채우지 않습니다.
- 직원 조회 API의 `phone_masked` 필드는 마스킹된 번호 또는 JSON `null`을 반환합니다. 직원 화면은 `null`을 ‘연락처 미보관’으로 표시합니다. 전체 번호가 필요한 지정 운영자는 별도 SSH 신원으로 카드 한 건과 용도를 요청합니다. 서버가 감사를 커밋한 뒤 암호문을 전달하고 지정 Mac의 개인키로 복호화합니다.
- **11/25 사용자 결정.** 미수령 상품 연락에 필요한 전체 번호의 암호화 보관을 유지합니다. 광고·판촉 사용은 제외합니다. 고객 UI에는 **‘개인정보 처리 안내를 확인했습니다.’** 한 칸만 두며 필수·선택 체크박스를 나누지 않습니다. 현재 합성 화면의 문구와 운영용 문구 적용은 별도입니다.

## 4. 기술적 선택 근거

동일 번호 검색에는 매번 같은 검색값이 필요하고, 연락에는 번호를 다시 읽을 수 있어야 합니다. 두 목적의 키를 분리하면 직원 검색 경로에 복호화 권한을 줄 필요가 없습니다. 카드·프로필·연락처·세션을 함께 저장해 연락처 저장 실패 시 불완전한 카드가 생기는 것도 막습니다. 이 설명은 구현에서 확인한 성질입니다.

## 5. 단점과 위험

가입 서버는 입력 순간 번호를 처리합니다. 서버와 HMAC 키가 함께 유출되면 번호 후보를 대조할 위험이 있고, 마스크에도 일부 숫자가 남습니다. 공개키 암호화는 조회 단말의 화면 촬영이나 운영자의 목적 외 이용까지 막지 못합니다. 감사의 ‘전달’과 ‘표시 확인’은 별도 결과이며 연결 중단 시 누가 실제로 읽었는지 단정할 수 없습니다. 복구용 개인키가 없으면 정상 암호문도 다시 읽을 수 없습니다.

**출시 차단 사항.** 미수령 연락이 계약 이행에 필요한 처리인지, 별도 동의가 필요한지 검토가 끝나지 않았습니다. 단일 체크박스는 안내 확인 기록입니다. 독립된 동의가 필요하다는 검토 결과가 나오면 가입을 열기 전에 현재 UI 결정과 조정해야 합니다. 과거 안내를 새 목적에 소급할 수 없습니다. 코드의 조회 용도 목록도 최종 운영 목적과 맞춰야 합니다.
