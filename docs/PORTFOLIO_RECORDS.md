# 포트폴리오 기록 원칙

이 프로젝트는 AI를 활용해 설계·구현·검수를 진행한 프로젝트입니다. 기록에서는 프로젝트 소유자가 제시한 요구사항, AI의 구현·검수 지원, 도구와 CI에서 확인한 결과, 개인이 직접 이해·재현한 경험을 구분합니다. 커밋 작성자만으로 코드를 직접 작성하거나 모두 이해했다고 판단하지 않습니다.

[ADR 목록](decisions/README.md) · [개발 로그](devlog/README.md) · [작성 템플릿](devlog/TEMPLATE.md)

## 무엇을 어디에 남기는가

| 문서 | 역할 | 중복을 피하는 방법 |
|---|---|---|
| 루트 README | 프로젝트 소개·현재 구조·진입점 | 상세 회고는 링크로 연결 |
| CHANGELOG | 버전별 변경 사실 | 의사결정 토론이나 개인 경험을 대신하지 않음 |
| TEST_REPORT / docs/evidence | 실행 환경·결과·한계 | 로그에서 필요한 결과만 근거로 인용 |
| docs/decisions | 어떤 문제에 어떤 선택을 적용했는지 | 운영 명령은 기존 설치/운영 문서에 연결 |
| docs/devlog | 문제·관측·가설·변경·검증의 연결 | 증상과 확인된 원인을 분리 |
| 기존 PR 템플릿 | 변경과 검증을 검토하는 진입점 | 해당 PR 설명에 ADR/로그 링크를 추가 |

이번 기록의 구현 기준은 [V1.4.0 커밋 1284c52](https://github.com/nuyhsp02/maison-de-gourmet-stamp/commit/1284c52e04e5e323af4a7fb182d78a2b27a01b8f)입니다. 이전 설계의 최초 날짜나 회의 기록이 없으면 현재 작성일을 과거 결정일로 사용하지 않습니다. 기존 태그/릴리스와 과거 문서를 새 회고에 맞춰 고쳐 쓰지 않습니다.

## 근거와 표현

- **확인:** 소스의 현재 동작, 특정 커밋의 변경, 실제 테스트 결과처럼 링크로 대조할 수 있는 사실.
- **사후 해석:** 현재 요구사항과 구현의 연결을 설명하는 판단. 당시 판단 과정과 동일했다고 주장하지 않음.
- **가설:** 재현/계측하지 않은 원인 후보. 해결된 원인으로 적지 않음.
- **미확인:** 발생일·검토 이력·개인 재현 등 근거가 부족한 내용. 빈칸을 추측으로 채우지 않음.
- **개선 후보:** 이후 비교/시험할 선택지. 이미 검토하거나 채택한 대안으로 적지 않음.

ADR의 대안도 이 기준을 따릅니다. 당시 비교 기록이 없으면 그 사실을 먼저 밝히고, 회고 시 비교 가능한 방안만 별도로 적습니다. 기술 선택의 근거는 현재 제약과 코드에서 확인되는 범위로 한정합니다.

## 참여 범위와 AI 활용

| 구분 | 현재 기록할 수 있는 범위 | 추가 확인이 필요한 범위 |
|---|---|---|
| 요구사항 분석 | 회원가입 없음·10종 수집·지급 1회·노트북 운영 등 소유자가 제시한 조건과 README의 정책 | 요구사항을 정한 현장 조사/고객 인터뷰의 실시 여부 |
| 기술 선택 | 기존 Flask/Waitress/SQLite 유지, 외부 설정/DB 분리 등 문서·코드의 선택 | 각 후보를 당시 직접 비교한 과정·비용/성능 실험 |
| 구현·검수 | AI 활용을 명시하고, 실제 diff·테스트·PR에 남은 결과를 연결 | 사람이 직접 작성한 줄 수, 함수별 독자 구현/이해 수준 |
| 오류 재현 | GitHub CI의 실패와 수정 후 통과를 구체적 실행 링크로 설명 | 동일 오류를 소유자가 개인 장비에서 직접 재현했는지 |
| 코드 이해 | 관련 함수/제약과 설명해야 할 질문을 제시 | 소유자가 직접 읽고 설명한 범위는 확인 후 본인이 기록 |

면접 준비 시 `init_db`, `collect`, `recover`, `redeem`, `snapshot` 등을 직접 읽고 입력·상태 변경·실패 경로를 설명해 봅니다. 자신이 실행한 명령, 이해한 근거, 아직 설명하기 어려운 부분을 날짜와 함께 추가하세요. 이 문서가 생겼다는 이유로 해당 학습이 끝났다고 표시하지 않습니다.

## 검증과 성과의 경계

- 합성 고객 400명/30개 병렬 애플리케이션 클라이언트 테스트는 실사용 고객 수나 실제 네트워크의 처리 성능이 아닙니다.
- Node의 DOM 모형·QR 픽셀/좌표 검사는 실제 렌즈·초점·권한·인앱 브라우저 검증이 아닙니다.
- Windows hosted runner의 Python 테스트와 PowerShell 파싱은 카페 Windows 10의 설치·로그인 전 부팅·터널 서비스 검증이 아닙니다.
- 파일 생성/설정 준비와 실제 설치·공개·운영 성공을 구분합니다. 실제 운영 실적·지급 건수·무중단 일수는 근거가 없으므로 기록하지 않습니다.
- 이전 테스트 결과를 인용했는지 이번에 새로 실행했는지, 실행자가 사람·AI 도구·CI 중 누구인지 함께 적습니다.

## 앞으로의 작성 순서

1. 실제 작업 브랜치에서 [개발 로그 템플릿](devlog/TEMPLATE.md)을 복사합니다. 발생일과 기록일, 실행자를 따로 적습니다.
2. 관측한 증상과 예상 동작을 먼저 적고, 원인 가설은 확인 상태를 붙입니다.
3. 변경 후 diff/커밋·명령·환경·결과 링크를 채웁니다. 실패 기록도 남기고, 불필요한 원본 로그 복사는 피합니다.
4. 장기적인 선택이 바뀌면 새 ADR을 작성하고 이전 ADR의 대체 관계를 표시합니다. 해결 과정은 로그에서 ADR로 연결합니다.
5. 기존 PR의 '바뀐 동작'과 '확인'에 기록 링크를 넣습니다. 현장 미검증을 남긴 채 기존 필수 CI를 통과한 후 병합합니다.
6. 새 기록을 해당 디렉터리 README 목록에 추가합니다. 결정이 바뀌지 않은 작은 작업마다 ADR을 만들 필요는 없습니다.

실제 QR·쿠키/복구 토큰·고객 DB/백업·운영 로그·개인 경로·인증정보가 담긴 캡처는 공개 기록에 넣지 않습니다. 비밀을 삭제한 다음 커밋만으로 이력에서 사라지지 않는다는 점은 [Git 안내](GIT_GUIDE.md)의 공개 전 확인 절차를 따릅니다.
