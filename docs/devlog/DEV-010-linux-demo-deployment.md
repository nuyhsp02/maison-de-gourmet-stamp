# DEV-010 · 기존 카드를 보존한 Ubuntu 비공개 DEMO 배포

- 기록 유형·기록일 — 배포 보고에 근거한 회고, 2026-11-25
- 작업일·기준 — 2026-11-20, Ubuntu DEMO `b4ecfc3 → ce0b22b`. 장애 발생일을 전제로 한 기록은 아닙니다.
- 상태·주체 — 사용자가 승인한 비공개 시연 환경에 Codex가 배포·검증한 결과입니다. 매장의 기존 DEMO 검수 완료는 사용자 확인입니다. 소유자가 직접 수행한 명령·코드 이해 범위는 미확인입니다.

## 1. 문제와 예상 동작

상품 QR 확인 전까지 적립하지 않고, 가입이나 카드 복구 뒤에도 같은 상품으로 돌아와야 했습니다. 매장에서 이미 쓰기로 한 QR 11개와 합성 고객의 기존 기록을 유지하면서 상품 10개의 정식명·간략명을 반영해야 했습니다.

## 2. 관측과 원인

기존 Linux DEMO에는 이미 QR 키·세션·복구 기록이 있었습니다. 상품명은 DB의 상품 키와 독립적으로 행사 설정에서 읽을 수 있었습니다. 이전 클라이언트는 자동 적립 POST를 보낼 수 있었고 서버 교체 뒤에도 열린 탭의 스크립트는 그대로 동작했습니다. 이는 V1.4 당시의 일반적인 캐시 문제 조사와 구별되는 후기 관측입니다. [상품·등록 확인 흐름](../../app/static/app.js) · [이전 캐시 조사](DEV-001-browser-cache-and-js-version.md)

## 3. 해결 또는 조사 과정

기존 비공개 HTTPS와 직원 인증을 유지하고 합성 자료만 쓴다는 조건에서, DB의 상품 ID에 맞춰 카탈로그를 연결했습니다. 기동 전 검사를 마친 코드 디렉터리만 교체했습니다. 보고서가 실제로 검토한 복구 선택지는 **코드 롤백**과 **손상된 DB의 격리 복원**입니다. 기능을 되돌릴 때 이전 DB까지 덮으면 배포 후 적립까지 사라지므로 최신 DB를 유지하는 코드 롤백을 준비했습니다. 당시 실제 롤백은 수행하지 않았습니다.

## 4. 코드/설정 변경

`98a8b76`의 적립·가입 확인 UX와 `ce0b22b`의 카탈로그를 함께 배포했습니다. 두 버전 사이 배포 범위(`b4ecfc3..ce0b22b`)는 17개 파일입니다. 기존 PR3에서 마련한 Linux 서비스·프록시는 재사용했습니다.
