## 같은 UID의 두 서비스

기존 백업 작업은 웹과 같은 `maison-prod`로 실행됐다. 백업 유닛에만 자격 경로를 설정해도 Linux는 같은 UID를 같은 파일 소유자로 취급한다. 반대로 백업 유닛의 사용자 이름만 바꾸면 원본 DB·프로필 키를 보호하는 0700/0600 소유자 검사에 걸린다. DB 권한을 넓히지 않고 이 두 조건을 함께 만족시켜야 했다. [파일 소유자 검사](../../deploy/linux/prod.py) · [웹 유닛](../../deploy/linux/maison-prod.service)

## 검증 근거

직전 설계 검증 기록은 Python 487/487, JavaScript 97/97, 백업 집중 회귀 26/26이었다. 공식 AWS CLI와 Signing Helper를 쓰되 TLS와 서명을 검증하는 로컬 시험 서버에서 16/16을 확인했다. 900초를 요청하고 응답 수명을 8초로 단축한 시험이었다. 실제 AWS의 IAM 정책 평가·CRL 전파 시간은 이 수치에 포함되지 않는다.

이번 검수에서 OpenSSL 3.6.2로 합성 365일 리프와 3년 시험 CA의 체인을 검사했다. 만료 30일 전 정각에 교체 대상이 됐고 만료 1초 전 검증 성공, 만료 1초 후 실패를 확인했다. 날짜는 검증기에 인자로 주고 개인키는 메모리에서만 생성했다.

설치된 botocore 1.36.3의 API 모델에서 `CreateProfile.durationSeconds`의 범위와 `CreateTrustAnchor`의 입력 항목을 확인했다. 전자는 900~43,200초이고 후자에는 리프 인증서 수명이 없다. `CreateSession`은 이 SDK 모델 밖에 있어 [AWS의 서명 요청 명세](https://docs.aws.amazon.com/rolesanywhere/latest/userguide/authentication-create-session.html)와 대조했다. 세션 900초와 리프 1년의 근거는 [인증 결정](../decisions/ADR-014-backup-workload-identity.md)에 기록했다.

## 실제 AWS에서 받을 증거

- Mac을 끈 상태에서 전송 UID가 새 세션을 받아 정상 수신 영수증을 게시하는지 확인한다. 백업 계정을 격리하고 누락 지표가 장애 통보로 이어지는지, 복구 주기 뒤 정상 통보가 도착하는지 실제 구독자가 확인한다.
- 폐기된 인증서로 신규 발급을 시도하는 시험과, **폐기 직전 발급된 세션**으로 승인된 합성 S3 버전을 읽는 시험을 분리한다. 후자는 역할의 기존 세션 차단을 적용한 뒤 재검증한다.
- 지정 Mac에서 MFA, 승인한 하나의 객체 버전과 복원 기한, 증거 쓰기·삭제 거부를 확인한다. 동기화된 시각, 인증서 갱신 책임자, 암호화 오프라인 복구 사본을 운영자가 인수한다.

## 직접 재현할 질문

1. UNIX 소켓에서 UID를 확인해야 하는 이유를 설명하고, 전송 계정이 원본 DB를 읽을 수 없는 상태에서 암호문을 받는 경로를 코드로 따라가 보자.
2. 클라이언트 키가 유출되면 900초 세션만으로 왜 피해를 제한할 수 없는가? CRL 갱신과 기존 역할 세션 회수의 서로 다른 성공 기준은 무엇인가?
3. 이미 업로드한 사본의 영수증 게시만 실패하도록 만든 뒤 재시도하자. 데이터 버킷에서 두 번째 버전 생성을 방지하는 조건과 독립 증거의 쓰기 권한을 확인하자.

운영자가 직접 수행한 날짜, 훈련 결과와 설명은 실제 인수 후 기록한다.
