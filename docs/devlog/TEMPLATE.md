# DEV-번호 · 구체적인 작업/문제 제목

- 기록 유형: 진행 기록 / 근거 기반 회고 / 조사·미확인 사례 중 선택
- 기록일: 실제 작성일
- 문제 발생일: 근거 링크와 날짜. 근거가 없으면 **미확인**
- 상태: 조사 중 / 재현 확인 / 수정 검증 / 현장 검증 대기 등
- 기준 브랜치/커밋:
- 실행 주체: 사람 직접 / AI 도구 실행 / GitHub CI / 미확인
- 소유자의 직접 확인·이해 범위: 실제 읽은 코드/설명/실행만 작성. 아직 확인하지 않았으면 미확인

## 1. 문제와 예상 동작

관측한 증상, 기대한 동작, 영향 범위를 구분합니다. 실제 사건 근거가 없으면 '문제 유형 조사'라고 표시합니다.

## 2. 관측과 원인

- 확인한 사실과 증거 링크:
- 원인 가설과 미확인 부분:
- 확인/기각한 방법:

로그/코드와 양립하는 가설이라는 이유만으로 원인 확정이라고 쓰지 않습니다.

## 3. 해결 또는 조사 과정

실제로 한 순서만 적습니다. 검토한 대안과 뒤늦게 떠올린 개선 후보를 분리합니다. 실패한 시도도 근거가 있으면 남깁니다.

## 4. 코드/설정 변경

변경 파일·함수·행동의 전후와 실제 diff/커밋 링크를 적습니다. 변경하지 않았다면 '코드 변경 없음'으로 씁니다. 기존 동작이 이 사건을 해결하려고 만들어졌다는 근거도 별도로 확인합니다.

## 5. 검증 결과

| 구분 | 환경/버전 | 명령 또는 실행 링크 | 관측 결과 | 이 결과로 확인하지 못하는 것 |
|---|---|---|---|---|
| 이번에 실제 실행 / 이전 결과 인용 | 실제 값 | 실제 증거 | 통과/실패/미실행 | 범위 |

임시 DB·합성 고객·모형 DOM·실제 HTTP·실물 기기를 구분합니다. 실패→수정→재실행이면 각각의 커밋/결과를 연결합니다. 경과 시간은 측정 근거가 있을 때만 적습니다.

## 6. 미검증 사항과 후속 확인

실제 단말·운영 배포·권한·현장 처리량 등 남은 검증과 그 완료 조건을 적습니다. 개선 후보는 완료 기능으로 쓰지 않습니다.

## 7. 관련 근거와 학습 확인

- 관련 ADR/기존 운영 문서:
- PR/커밋/CI:
- 증거 파일(공개 가능한 요약만):
- 직접 설명해 볼 질문:
- 소유자가 실제로 설명/재현한 기록: 확인 후 본인이 날짜·범위·근거를 추가

실제 QR, 고객 화면의 개인 정보, 세션/복구 토큰, 운영 DB/백업/로그, 인증정보는 넣지 않습니다. 비밀을 지운 모형/요약과 관련 코드로 설명합니다.
