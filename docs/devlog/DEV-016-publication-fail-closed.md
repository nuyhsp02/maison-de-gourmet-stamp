# DEV-016 · 공개 절차 Fail-Closed 및 보안 검수 강화

- 2026-11-25 로컬 개발·검증 기록. 브랜치는 `feature/contact-privacy-admin`, 검사한 커밋은 `bbfb27b`다. 이 글과 이번 도구 변경은 검사 당시 작업 트리에 있었다.
- 사용자는 공개 검사가 불완전하면 전송을 중단하고 비공개 값·개인키·파일명을 보호하도록 결정했다. Codex가 코드와 운영 기록을 대조하고 구현·로컬 시험을 수행했다. 사용자의 독립 재현 여부는 미확인이다.

## 1. 문제와 예상 동작

기존 Git 안내에는 검사와 전송이 서로 독립된 명령으로 적혀 있었다. 검사 실패를 본 사용자가 다음 명령을 실행하면 전송될 수 있었다. 후보에 들어갈 모든 과거 파일을 검사하고, 승인한 SHA와 실제 대조한 자료를 확인한 뒤에만 한 브랜치를 전송할 수 있어야 했다. 이전 검토에서 실제 오전송이나 키 유출을 관측한 적은 없다. [이전 이력 검사](DEV-015-public-history-and-asset-permission.md)

## 2. 관측과 원인

- 일반 패턴은 파일 형식과 자격정보의 흔한 표현을 식별하지만 비공개 페이지의 짧은 문맥 없는 식별자나 특정 운영 주소가 어떤 프로젝트에 속하는지 스스로 판단하지 못한다. 이전 안내의 기본 명령은 별도 대조 자료 없이도 성공할 수 있었다.
- 운영자용 Mac 도구는 암호화 개인키와 재암호화한 복구 사본을 같은 바이너리 형식으로 저장하고 출력 파일명은 운영자가 지정한다. 파일 확장자만 검사하면 다른 이름으로 저장된 보관본을 놓칠 수 있었다. [Mac 키 생성·복구](../../tools/contact_mac.py) · [서버의 공개키 사용](../../app/contact_privacy.py) · [키 관리 절차](../CONTACT_PRIVACY.md)
- 패키저가 항목을 거부할 때 예외에 파일명을 넣고 있었다. 파일명에 개인정보가 있으면 오류 출력도 공개 대상이 될 수 있다. 합성 이름을 사용해 새 오류 출력을 검증했다.

## 3. 해결 또는 조사 과정

1. 브랜치 이름을 검사 시작과 끝에서 승인 SHA와 대조하고, 지정한 공개 경계가 후보의 조상인지 확인했다. 검사 중 SHA가 바뀌면 결과를 폐기한다.
2. 기존 비공개 이력·배포 기록에서 이전에 검토한 대조값 7개를 확인했다. 내용 전체를 노출할 필요 없이 표준 입력으로 비교하고, 사전에 검토한 개수와 원본 파일의 SHA-256을 모두 검사한다. 이 목록은 저장소 밖의 소유자 전용 위치에 보존했다.
3. 다른 참조에 남은 문제 객체도 재검사한다. 후보에서 도달하지 못하고 객체·경로·규칙 목록이 독립적으로 검토한 목록과 일치해야 한다. 바뀐 발견 건이 있으면 전체 참조의 결과부터 다시 검토한다.
4. Git 안내를 모의 명령으로 실행하던 중 복합 조건의 SHA 비교가 실패한 뒤에도 셸이 다음 줄로 진행하는 경우를 재현했다. 조건마다 중단을 명시한 뒤 같은 상황에서 모의 전송 호출 0회를 확인했다. 실제 원격에는 전송하지 않았다.

## 4. 코드/설정 변경

- [공개 검수 도구](../../tools/audit_public.py)에 `--publication`을 추가했다. 승인된 전체 ref·SHA·공개 경계와 보호된 표준 입력의 지문·개수가 필수다. 후보 검사, 모든 참조의 발견 건 확인, 최종 SHA 확인이 끝나야 성공한다.
- Mac 전용 개인키는 헤더와 92바이트 레이아웃으로 식별한다. PEM 형식 등 개인키 헤더와 기존 비공개 파일 제한도 적용한다. 정상 서버용 공개키 JSON, 공개키 헤더와 문서 속 형식 설명은 각각 합성 예제로 구분했다.
- [Release 패키저](../../tools/build_release.py)는 거부한 항목의 이름·경로·Git 오류 원문 대신 안전한 오류 코드와 필요한 경우 트리 항목 번호를 반환한다. [공개 전 절차](../GIT_GUIDE.md#공개-후보와-비공개-보관-이력을-함께-쓰는-경우)는 기본 검사 모드와 사용자 승인 뒤 단일 SHA 전송을 구분한다.
- 현재 카탈로그의 상품 10종, 초기 Windows의 무가입 구조와 후속 PR 1 프로필, 직원 API의 마스크 또는 JSON `null`과 화면의 ‘연락처 미보관’ 표시를 구분해 설명을 바로잡았다. [카탈로그](../../app/demo-product-catalog.json) · [직원 API](../../app/staff_admin.py) · [직원 화면](../../app/static/admin.js)

## 6. 미검증 사항과 후속 확인

이번 대조 목록에는 실제 고객 DB 행, 운영 QR·세션 원문, 운영 비밀번호·키 원문이 없다. 누구의 이름인지 또는 암호화 파일에 무엇이 들어 있는지는 일반 패턴 검사만으로 판별할 수 없다. 전화번호 형태가 있는 합성 시험 파일과 이미지의 화면 내용은 사람이 출처를 검토할 대상이다. 미커밋 문서와 도구를 포함하는 최종 SHA는 아직 없으며, 두 커밋을 승인한 뒤 같은 검사와 백업을 다시 수행해야 한다. 실제 GitHub 전송·PR·Release·PROD 배포는 별도 승인 사항이다.
